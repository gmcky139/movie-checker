# 映画館実データ取得・公開仕様書

- 対象リポジトリ: `gmcky139/movie-checker`
- 文書バージョン: 2.0
- 更新日: 2026-08-03
- 公開先: GitHub Pages
- ローカル実行: WSL上のDocker Engine

## 1. この文書の目的

本書は、映画上映情報アプリで実際の上映予定を取得し、正規化、検証、表示、GitHub
Pagesへの公開まで安全に行うための追加仕様である。

`docs/movie_app_prototype_spec.md`は基本的な画面、URL、データ構造、静的サイト、Docker、
テストの要件として引き続き有効とする。ただし、実データ取得、作品名正規化、データモード
別表示、GitHub Pages公開、ローカル検証方法について本書と旧仕様が矛盾する場合、本書を
優先する。

特に、旧仕様にある次の方針は本書によって置き換える。

- GitHub Pagesを常にサンプルモードで公開する方針
- 実データを手動検証だけに限定する方針
- すべての上映情報やリンクをデモと表示する方針
- WSLホスト上で直接Node.jsやnpmを実行する検証手順

## 2. 目的と完成像

GitHub Pages上で、次の3館について現在の公式上映予定を横断して確認できるようにする。

1. 109シネマズ名古屋
2. ミッドランドスクエアシネマ
3. イオンシネマ常滑

利用者は、今日を含む4日間を切り替え、作品名で検索し、作品別または映画館別に上映時刻を
確認できる。公式レスポンスから安全に取得できた場合は、公式の予約または上映案内ページへ
移動できる。

本アプリは購入処理を行わず、公式情報の正確性を保証しない。上映内容は変更される可能性が
あるため、購入前に公式サイトで再確認できる表示を設ける。

## 3. ユーザーによる許可範囲

ユーザーは、本書に従い、対象3館の公式サイトから取得した上映予定の事実情報をGitHub
Pagesで公開することを許可している。

許可は次に限定される。

- 対象3館の上映予定
- 無料で公開され、認証を必要としない公式ページまたは公式データ
- 本アプリの上映予定表示に必要な事実情報
- 低頻度のGitHub Actions定期更新

次は許可されていない。

- 有料APIまたは有料データサービス
- 対象外の映画館
- 検索エンジンや上映情報集約サイトからの取得
- ログイン、認証、CAPTCHA、アクセス制限の回避
- 公式ポスター、ロゴ、場面写真、あらすじ、キャスト、記事などの複製または直リンク
- 予約、決済、座席確保を本アプリ内で行うこと

長期運用では、各公式サイトの利用条件や表示方針に変更がないかを人間が定期的に確認する。
取得を拒否する応答が返った場合は、回避せず停止する。

## 4. データモード

アプリは次の2モードを維持する。

| モード | 用途 | 表示 |
|---|---|---|
| `sample` | オフライン開発、決定的テスト、デモ | サンプルであることを明記する |
| `real` | GitHub Pages公開、実データ確認 | 公式情報由来、取得日時、注意事項を表示する |

サンプルモードは削除しない。GitHub Pagesのpush、手動実行、定期実行による公開ビルドは
`real`モードを使用する。

実データ取得失敗時にサンプルデータへ自動で切り替えて公開してはならない。更新失敗時は
デプロイを中止し、直前に成功したPagesをそのまま維持する。

## 5. 取得対象

### 5.1 109シネマズ名古屋

- provider ID: `cinema109-nagoya`
- theater ID: 実装中の既存IDを維持する
- 基本取得URL:
  `https://cinema.109cinemas.net/cgi-bin/pc/site/det.cgi?tsc=1149&ymd=YYYY-MM-DD`
- 文字コード: EUC-JPを想定し、UTF-8へ安全に変換してから解析する

日付ごとの公式HTMLから、作品名、上映日、開始・終了時刻、スクリーン、上映形式、販売状態、
公式レスポンスに含まれる安全な予約URLを取得する。

### 5.2 ミッドランドスクエアシネマ

- provider ID: `midland-square`
- theater ID: 実装中の既存IDを維持する
- 日付一覧:
  `https://ticket.midlandcinema.jp/schedule/schedule/pc/s0100_0201_DateList.html`
- 日付別スケジュール: 日付一覧または既知の公式規則から得られる公式ページ

作品名、上映日、開始・終了時刻、スクリーン、上映形式、販売状態を取得する。予約URLが
`onclick`などへ埋め込まれている場合もJavaScriptを実行してはならない。許可された単純な
`window.open`引数などを文字列として解析し、HTTPSとホストを再検証する。

### 5.3 イオンシネマ常滑

- provider ID: `aeon-tokoname`
- theater ID: 実装中の既存IDを維持する
- 公式スケジュールJSON:
  `https://theater.aeoncinema.com/schedule/v2/data/tokoname/schedule.json`

JSONに含まれる作品名、日時、スクリーン、上映形式、販売状態などを取得する。ISO 8601日時は
文字列の一部を切り出さず、時点として解析して`Asia/Tokyo`の上映日と時刻へ変換する。

安全な上映回別予約URLが公式データから得られない場合、URLを推測して作らない。上映時刻を
非リンクにするか、明示的に設定した公式映画館ページへ案内する。

## 6. 許可ホスト

取得先とリダイレクト先は次に限定する。

- `cinema.109cinemas.net`
- `109cinemas.net`
- `ticket.midlandcinema.jp`
- `www.midland-sq-cinema.jp`
- `midland-sq-cinema.jp`
- `theater.aeoncinema.com`
- `www.aeoncinema.com`
- `aeoncinema.com`

URLは`URL`として解析し、HTTPS、ホスト名、ポート、リダイレクト先を検証する。文字列の
部分一致だけで許可してはならない。ユーザー情報を含むURL、HTTP、未知のポート、許可外
ホストは拒否する。

## 7. 取得可能な項目

必要に応じて次の事実情報を取得できる。

- 作品名
- 上映日
- 開始時刻
- 終了時刻
- 上映時間
- スクリーン名または番号
- 字幕、吹替、IMAX、4DX、SCREENX、Dolbyなどの上映形式
- 販売状態
- 公式レスポンスから安全に得た予約URL
- 映画館名と公式サイトURL
- 情報元URL
- 取得日時

不明な終了時刻、上映時間、販売状態、形式を推測してはならない。データ構造で省略可能に
するか、UIで中立的に表示する。

## 8. HTTP取得方針

HTTP処理は共通クライアントへ集約し、次を満たす。

- HTTPSのみ
- 取得元と全リダイレクト先のallowlist検証
- 1リクエストあたり約15秒のタイムアウト
- 最大2同時接続
- レスポンスサイズ上限
- 同一更新内の同一URLは1回だけ取得
- Cookie、認証情報、ブラウザプロファイルを送信しない
- リポジトリまたはアプリを正直に示す控えめなUser-Agent
- HTMLまたはJSONとして妥当でないレスポンスを拒否
- エラー本文を無制限にログ出力しない

リトライは、一時的ネットワークエラーと5xxに限り最大2回とする。待機時間は短い指数
バックオフとし、同時リクエスト数の上限を守る。

次はリトライしない。

- 400系の通常エラー
- 401、403、404、429
- CAPTCHAまたはアクセス拒否ページ
- 許可外リダイレクト
- レスポンスサイズ超過
- 解析不能な構造

403または429を別User-Agent、プロキシ、ブラウザ自動化などで回避してはならない。

## 9. Provider構造

映画館固有処理を個別アダプターへ分け、共通の生データ型へ変換する。

概念上の共通フィールドは次のとおりとする。

```ts
type RawScreening = {
  providerId: string;
  theaterId: string;
  theaterName: string;
  sourceUrl: string;
  rawTitle: string;
  date: string;
  startTime: string;
  endTime?: string;
  runtimeMinutes?: number;
  screenName?: string;
  formats: string[];
  salesStatus?: string;
  reservationUrl?: string;
};
```

既存の型名や構造が同等の責務を果たしている場合、名前を合わせるためだけの大規模変更は
行わない。

Providerは、取得、文字コード変換、構造解析、公式URL抽出までを担当する。複数映画館の
統合、作品名正規化、作品ID生成、重複除去、最終スキーマ変換は共通処理へ分離する。

## 10. 日付と時刻

- 対象範囲は`Asia/Tokyo`における今日、明日、2日後、3日後とする。
- GitHub ActionsのUTC環境でも日本の日付を基準にする。
- `now`を引数として渡せる設計にしてテスト可能にする。
- ISO日時は時点として解析してから日本時間へ変換する。
- 日付をまたぐ終了時刻や深夜上映を正しく扱う。
- 公式サイトが対象日の予定をまだ公開していない場合、存在しない上映を生成しない。
- UIはデータに存在する日付と4日タブの整合を安全に処理する。

## 11. 作品名正規化

同一作品が映画館ごとの表記差で別作品に分割されないよう、正規化を共通処理で行う。

### 11.1 基本正規化

少なくとも次を順序を固定して適用する。

1. Unicode NFKC正規化
2. 前後空白の除去
3. 全角空白、タブ、連続空白の単一半角空白化
4. 装飾用の`『』`、`「」`、引用符など外側の囲みを除去
5. コロン、スラッシュ、中点、波ダッシュ、ハイフン類などの表記を管理可能な形へ統一
6. 確実に識別できる上映形式を作品名から分離
7. 再度空白と前後記号を整理
8. 明示エイリアスを適用

### 11.2 上映形式の分離

括弧の有無にかかわらず、作品名の先頭または末尾に付く次のような形式を認識できるように
する。

- 字幕、字幕版
- 吹替、吹替版、日本語吹替
- IMAX、IMAXレーザー
- 4DX
- SCREENX
- Dolby Cinema、Dolby Atmos
- 2D、3D

形式は上映回の`formats`へ保持する。形式を除去した結果だけで異なる作品を誤統合しないよう
テストする。

### 11.3 統合方法

作品の統合は次に限定する。

1. 正規化後の完全一致
2. 安全な規則ベース一致
3. レビュー可能な明示エイリアス表
4. 一意性がテストで確認された切り詰め表記の対応

編集距離だけの曖昧一致や生成AIによる自動統合は行わない。似た題名の別作品を統合する
危険があるためである。

公式ページで末尾が`...`などに切り詰められた題名は、他候補に同じ接頭辞がなく、対応が
テストで明示されている場合だけ統合する。判断できない場合は別作品として保持し、ログまたは
検証結果へ警告を出す。

少なくとも、実データで確認された次のような差をテスト対象に含める。

- `Michael/マイケル`、`『Michael マイケル』`、`字幕 Michael マイケル`
- Spider-Manの空白、コロン、副題、字幕・吹替表記
- クレヨンしんちゃんの装飾記号、形式、切り詰め表記
- Star Warsの句読点や区切り記号
- 仮面ライダー／ギャバンの長題・短縮表記

具体的なエイリアスはソースコード上の小さな表へ集約し、理由とテストを付ける。データ取得の
たびに変わる手動IDを生成してはならない。

### 11.4 決定的ID

作品IDは正規化された代表名など安定した入力から決定的に生成する。同じ作品は、取得順、
映画館、実行時刻が変わっても同じIDになる。

ハッシュを使用する場合も、衝突、空文字、Unicodeをテストする。既存の詳細ページURLを
不必要に壊さない。

## 12. 重複除去

同一映画館、同一作品、同一日、同一開始時刻、同一スクリーン、同一形式の上映回が複数回
登録されないようにする。

同じ開始時刻でもスクリーンまたは形式が異なる場合は別上映として保持する。予約URLの有無
だけで上映を重複させず、安全な公式URLを優先して統合する。

## 13. 生成データと情報元

生成JSONには少なくとも次を含める。

- `dataMode`
- `generatedAt`
- `movies`
- `theaters`
- `screenings`
- `sources`

`sources`は各Providerについて次を記録する。

- `providerId`
- `theaterId`
- `theaterName`
- `sourceUrl`
- `fetchedAt`
- `status`
- 必要に応じて取得件数または安全なエラー概要

時刻は機械可読な一貫した形式で保存する。UI表示時に日本語表記へ変換する。

## 14. 更新の原子性と失敗方針

更新処理は次の順番とする。

1. 一時領域へ3館のデータを取得
2. 各Providerの解析結果を検証
3. 作品名と上映形式を正規化
4. 重複を除去
5. 最終スキーマへ変換
6. 全体を実データ用ルールで検証
7. すべて成功した場合だけ最終JSONへ原子的に置換

次の場合は失敗とし、既存の有効データを上書きしない。

- 1館でも取得または解析に失敗
- Providerの結果が0件
- 対象3館のいずれかが最終データに存在しない
- 必須フィールド欠落
- 不正な日付または時刻
- 重複IDまたは参照切れ
- 許可外URL
- HTMLエラーページや異常なJSON
- 解析構造の重大な変化

公式側が対象4日すべてをまだ公開していない可能性は考慮する。各日付に必ず上映があると
仮定して架空データを補わない。ただし、Provider全体が0件なら成功扱いにしない。

エラーにはProvider名、映画館名、情報元URL、取得・解析・検証のどの段階かを含める。
Cookie、トークン、レスポンス全文、個人情報は含めない。

## 15. UI表示

### 15.1 実データモード

`dataMode === "real"`では次を表示する。

- 実際の公式上映情報を表示していること
- 最終取得または更新日時
- 情報元映画館名と安全な公式リンク
- 上映予定が変更される可能性
- 購入前に公式サイトで確認する案内

実データモードで次の表現を表示してはならない。

- デモ上映
- デモ予約ページ
- デモ用リンク
- サンプル上映情報
- DEMO SCHEDULE
- デモポスター

プレースホルダー画像の代替テキストは`ポスター画像なし`など中立的な表現にする。

安全な予約URLがある上映時刻は公式サイトへリンクする。URLがない場合は上映時刻を通常の
テキストまたはボタンではない要素として表示し、クリック可能に見せない。

### 15.2 サンプルモード

`dataMode === "sample"`では次を明記する。

- デモまたはサンプルデータであること
- 実際の上映・予約情報ではないこと
- 予約リンクがデモの場合は、そのことが分かるラベル

### 15.3 共通表示

- 現在の検索、4日タブ、作品詳細、映画館詳細、レスポンシブ表示を維持する。
- 選択日と検索語をURLへ保持する。
- 不正ID、不正日付、空データ、検索結果なしを白画面にしない。
- 外部リンクは公式サイトであることを分かるようにする。
- 見出し、ラベル、フォーカス、キーボード操作、代替テキストを維持する。
- 画面の大規模な再デザインは行わない。

## 16. GitHub ActionsとPages公開

`.github/workflows/deploy-pages.yml`は次のイベントで動作する。

- `main`へのpush
- `workflow_dispatch`
- 定期実行

定期実行はおおむね6時間ごとを上限の目安とし、公式サイトへ過剰にアクセスしない。

公開ビルドは次の順序を守る。

1. checkout
2. Node.jsセットアップ
3. `npm ci`
4. `DATA_MODE=real`で3館の実データ取得
5. 実データ全体の検証
6. Lint
7. Prettierの変更なしチェック
8. 非watchモードのテスト
9. TypeScriptとViteビルド
10. Pages artifactのアップロード
11. Pagesデプロイ

生成と検証は必ずartifactアップロードより前に行う。ビルド処理がサンプルデータを再生成して
実データを上書きしないようにする。

いずれかの処理が失敗した場合、artifactアップロードとdeployを実行しない。サンプルまたは
一部映画館だけのデータへ切り替えない。これにより、前回成功したPagesを維持する。

実データ確認用の別ワークフローは手動実行に限定し、生成JSONと`dist`を短期間のartifactと
して保存できる。ただしPagesへデプロイしない。

ワークフローは最小権限、Pages用concurrency、公式Actions、固定したNodeメジャーバージョン、
lockfileキャッシュを使用する。失敗ログから原因を確認できるようにする。

## 17. Docker仕様

WSLホストへNode.jsやnpmを導入しない。ローカルのJavaScript関連処理はDocker内で行う。

DockerfileはNode.jsビルドステージとNginxランタイムステージを持ち、ビルドステージで次を
実行する。

- `npm ci`
- 指定モードのデータ生成
- データ検証
- Lint
- `format:check`
- `test:run`
- TypeScriptチェック
- Viteビルド

サンプルと実データの双方をビルド引数`DATA_MODE`などで選択できるようにする。

```bash
docker build --build-arg DATA_MODE=sample -t movie-checker:sample .
docker build --build-arg DATA_MODE=real -t movie-checker:real .
```

実データモードでのCompose起動例:

```bash
DATA_MODE=real docker compose up --build -d
docker compose ps
```

Windows側ブラウザから`http://localhost:8080/`へアクセスできることを確認する。確認後は停止
する。

```bash
docker compose down
```

リポジトリのソースをNginxランタイムへ不要に含めず、`dist`だけを配信する。Nginxには
ヘルスチェックを設定する。

## 18. テスト仕様

公式ページ全体をfixtureとして保存しない。必要最小限の人工HTMLまたはJSONを用い、ネット
ワークなしで再現可能なProviderテストを作る。

### 18.1 Providerテスト

各Providerについて次を確認する。

- 正常な1作品・複数上映の解析
- 複数作品と複数スクリーン
- 上映形式の抽出
- 開始・終了時刻
- 深夜または日付境界
- 欠落フィールド
- 空レスポンス
- 不正HTMLまたはJSON
- 公式側の軽微な構造差
- 許可外予約URLの破棄
- 同一上映の重複除去

109シネマズではEUC-JP変換、ミッドランドではJavaScript非実行のリンク抽出、イオンでは
ISO日時から日本時間への変換を個別にテストする。

### 18.2 HTTPテスト

- HTTPS以外を拒否
- 完全なホストallowlist
- リダイレクト先再検証
- タイムアウト
- レスポンスサイズ上限
- ネットワークエラーと5xxの限定リトライ
- 403と429をリトライしない
- Cookieと認証情報を送らない

### 18.3 正規化テスト

- NFKC
- 全角・連続空白
- 装飾括弧
- コロン、スラッシュ、中点、波ダッシュ
- 括弧なしの字幕・吹替接頭辞
- IMAX、4DX、SCREENX、Dolbyなどの形式分離
- 明示エイリアス
- 切り詰めタイトルの一意対応
- 類似した別作品を統合しないこと
- 取得順に依存しない決定的ID

### 18.4 統合・UIテスト

- 3館すべて成功した場合だけ最終データを作る
- 1館失敗時に既存JSONを上書きしない
