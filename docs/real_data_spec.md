# 映画館実データ取得・公開仕様書

- 対象リポジトリ: `gmcky139/movie-checker`
- 文書バージョン: 2.1
- 更新日: 2026-08-04
- 公開先: GitHub Pages
- ローカル実行: WSL上のDocker Engine

## 1. この文書の目的

本書は、映画上映情報アプリで実際の上映予定を取得し、TMDBから正しく照合したポスターを
付与し、正規化、検証、表示、GitHub Pagesへの公開まで安全に行うための追加仕様である。

`docs/movie_app_prototype_spec.md`は基本的な画面、URL、データ構造、静的サイト、Docker、
テストの要件として引き続き有効とする。ただし、実データ取得、TMDBポスター、作品名正規化、
データモード別表示、GitHub Pages公開、ローカル検証方法について本書と旧仕様が矛盾する
場合、本書を優先する。

特に、旧仕様にある次の方針は本書によって置き換える。

- GitHub Pagesを常にサンプルモードで公開する方針
- 実データを手動検証だけに限定する方針
- すべての上映情報やリンクをデモと表示する方針
- WSLホスト上で直接Node.jsやnpmを実行する検証手順
- 外部映画APIとすべての外部ポスターを一律に禁止する方針

## 2. 目的と完成像

GitHub Pages上で、次の3館について現在の公式上映予定を横断して確認できるようにする。

1. 109シネマズ名古屋
2. ミッドランドスクエアシネマ
3. イオンシネマ常滑

利用者は、今日を含む3日間を切り替え、作品名で検索し、作品別または映画館別に上映時刻を
確認できる。公式レスポンスから安全に取得できた場合は、公式の予約または上映案内ページへ
移動できる。通常の映画作品には、保守的に照合できたTMDBのポスターを表示する。ポスターは
本アプリの主要機能であり、単なる装飾として扱わない。

本アプリは購入処理を行わず、公式情報の正確性を保証しない。上映内容は変更される可能性が
あるため、購入前に公式サイトで再確認できる表示を設ける。

## 3. ユーザーによる許可範囲

ユーザーは、本書に従い、対象3館の公式サイトから取得した上映予定の事実情報をGitHub
Pagesで公開し、非商用のDeveloper APIとしてTMDBを作品識別とポスター表示に利用することを
許可している。

許可は次に限定される。

- 対象3館の上映予定
- 無料で公開され、認証を必要としない公式ページまたは公式データ
- 本アプリの上映予定表示に必要な事実情報
- 低頻度のGitHub Actions定期更新
- TMDBの映画検索、作品ID、ポスターパス、画像設定
- TMDBが定める帰属表示に必要な承認済みロゴ

次は許可されていない。

- 有料APIまたは有料データサービス
- 対象外の映画館
- 検索エンジンや上映情報集約サイトからの取得
- ログイン、認証、CAPTCHA、アクセス制限の回避
- 映画館サイトやTMDB以外からのポスター、ロゴ、場面写真の複製または直リンク
- TMDBのあらすじ、キャスト、評価、レビュー、動画などポスター表示に不要なメタデータ
- 予約、決済、座席確保を本アプリ内で行うこと

長期運用では、各公式サイトとTMDBの利用条件や表示方針に変更がないかを人間が定期的に
確認する。取得を拒否する応答が返った場合は、回避せず停止する。本アプリを将来商用化する
場合は、無料の非商用Developer APIをそのまま利用せず、TMDBへライセンスを確認する。

## 4. データモード

アプリは次の2モードを維持する。

| モード | 用途 | 表示 |
|---|---|---|
| `sample` | オフライン開発、決定的テスト、デモ | サンプルであることを明記する |
| `real` | GitHub Pages公開、実データ確認 | 公式情報由来、取得日時、注意事項を表示する |

サンプルモードは削除しない。GitHub Pagesのpush、手動実行、定期実行による公開ビルドは
`real`モードを使用する。

実データ取得失敗時にサンプルデータへ自動で切り替えて公開してはならない。1館または2館が
失敗した場合は成功した映画館だけの上映を公開し、失敗館の状態を明示する。全3館の失敗、
または取得後の正規化・TMDB・検証・テスト・ビルド失敗時はデプロイを中止し、直前に成功した
Pagesをそのまま維持する。

## 5. 取得対象

### 5.1 109シネマズ名古屋

- provider ID: `cinema109-nagoya`
- theater ID: 実装中の既存IDを維持する
- 基本取得URL:
  `https://cinema.109cinemas.net/cgi-bin/pc/site/det.cgi?tsc=1149&ymd=YYYY-MM-DD`
- 文字コード: EUC-JPを想定し、UTF-8へ安全に変換してから解析する

日付ごとの公式HTMLから、作品名、上映日、開始・終了時刻、スクリーン、上映形式、販売状態、
公式レスポンスに含まれる安全な予約URLを取得する。

### 5.2 ミッドランドスクエアシネマ

- provider ID: `midland-square`
- theater ID: 実装中の既存IDを維持する
- 日付一覧:
  `https://ticket.midlandcinema.jp/schedule/schedule/pc/s0100_0201_DateList.html`
- 日付別スケジュール: 日付一覧または既知の公式規則から得られる公式ページ

作品名、上映日、開始・終了時刻、スクリーン、上映形式、販売状態を取得する。予約URLが
`onclick`などへ埋め込まれている場合もJavaScriptを実行してはならない。許可された単純な
`window.open`引数などを文字列として解析し、HTTPSとホストを再検証する。

### 5.3 イオンシネマ常滑

- provider ID: `aeon-tokoname`
- theater ID: 実装中の既存IDを維持する
- 公式スケジュールJSON:
  `https://theater.aeoncinema.com/schedule/v2/data/tokoname/schedule.json`

JSONに含まれる作品名、日時、スクリーン、上映形式、販売状態などを取得する。ISO 8601日時は
文字列の一部を切り出さず、時点として解析して`Asia/Tokyo`の上映日と時刻へ変換する。

安全な上映回別予約URLが公式データから得られない場合、URLを推測して作らない。上映時刻を
非リンクにするか、明示的に設定した公式映画館ページへ案内する。

## 6. 許可ホスト

取得先とリダイレクト先は次に限定する。映画館情報取得とTMDB取得のallowlistは用途別に
分け、TMDBホストを映画館スケジュール取得には使用しない。

- `cinema.109cinemas.net`
- `109cinemas.net`
- `ticket.midlandcinema.jp`
- `www.midland-sq-cinema.jp`
- `midland-sq-cinema.jp`
- `theater.aeoncinema.com`
- `www.aeoncinema.com`
- `aeoncinema.com`
- `api.themoviedb.org`
- `image.tmdb.org`
- `www.themoviedb.org`

URLは`URL`として解析し、HTTPS、ホスト名、ポート、リダイレクト先を検証する。文字列の
部分一致だけで許可してはならない。ユーザー情報を含むURL、HTTP、未知のポート、許可外
ホストは拒否する。

## 7. 取得可能な項目

必要に応じて次の事実情報を取得できる。

- 作品名
- 上映日
- 開始時刻
- 終了時刻
- 上映時間
- スクリーン名または番号
- 字幕、吹替、IMAX、4DX、SCREENX、Dolbyなどの上映形式
- 販売状態
- 公式レスポンスから安全に得た予約URL
- 映画館名と公式サイトURL
- 情報元URL
- 取得日時
- 保守的に照合したTMDB movie ID
- TMDBの`poster_path`から構築した検証済み画像URL
- ポスター照合状態と取得率

不明な終了時刻、上映時間、販売状態、形式を推測してはならない。データ構造で省略可能に
するか、UIで中立的に表示する。

## 8. HTTP取得方針

HTTP処理は共通クライアントへ集約し、次を満たす。

- HTTPSのみ
- 取得元と全リダイレクト先のallowlist検証
- 1リクエストあたり約15秒のタイムアウト
- 最大2同時接続
- レスポンスサイズ上限
- 同一更新内の同一URLは1回だけ取得
- 映画館ProviderへCookie、認証情報、ブラウザプロファイルを送信しない
- TMDB Bearer Tokenは`api.themoviedb.org`へのTMDB APIリクエストだけへ送る
- リポジトリまたはアプリを正直に示す控えめなUser-Agent
- HTMLまたはJSONとして妥当でないレスポンスを拒否
- エラー本文を無制限にログ出力しない

リトライは、一時的ネットワークエラーと5xxに限り最大2回とする。待機時間は短い指数
バックオフとし、同時リクエスト数の上限を守る。

次はリトライしない。

- 400系の通常エラー
- 401、403、404、429
- CAPTCHAまたはアクセス拒否ページ
- 許可外リダイレクト
- レスポンスサイズ超過
- 解析不能な構造

403または429を別User-Agent、プロキシ、ブラウザ自動化などで回避してはならない。

## 9. TMDBポスター取得

### 9.1 用途と認証

TMDBは作品識別とポスター表示だけに使用する。上映時刻、映画館、予約、評価、レビュー、
キャスト、あらすじ、動画、配信サービス情報は取得しない。

認証にはTMDBの`API Read Access Token`を使用し、環境変数名を次に固定する。

```text
TMDB_API_READ_TOKEN
```

GitHub Actionsでは同名のRepository Secretから、実データ生成ステップだけへ渡す。

```yaml
env:
  DATA_MODE: real
  TMDB_API_READ_TOKEN: ${{ secrets.TMDB_API_READ_TOKEN }}
```

Bearer Tokenは`Authorization`ヘッダーで`https://api.themoviedb.org`だけへ送る。URLの
クエリ、ログ、例外、生成JSON、HTML、ブラウザJavaScript、テストfixture、Dockerの`ARG`・
永続`ENV`へ含めない。Token未設定、401、403は設定不備として直ちに失敗させる。

### 9.2 問い合わせ

作品名正規化と映画館間の統合を先に完了し、一意な代表作品ごとにTMDBを問い合わせる。
基本検索は`GET /3/search/movie`とし、次を指定する。

- `query`: 上映形式と装飾を除いた代表作品名
- `language=ja-JP`
- `region=JP`
- `include_adult=false`

同一実行中の同一検索をキャッシュする。通常は1作品1検索とし、日本語検索で信頼できる候補が
得られない場合だけ、管理された別名または原題で追加検索する。無制限な検索語変形や全候補の
詳細取得は行わない。

画像ベースURLと利用可能サイズは`GET /3/configuration`を実行ごとに1回取得して確認する。
一覧と詳細で共用できる`w500`相当を基本とし、対応サイズがなければ設定レスポンス内の最も
近い安全なサイズを選ぶ。画像URLを文字列連結だけで信用せず、最終URLがHTTPSかつ
`image.tmdb.org`であることを検証する。

### 9.3 照合

検索結果の先頭を無条件に採用してはならない。誤ったポスターは未取得より悪いものとして
扱う。候補選択は、次の検証可能な情報に限定する。

1. 正規化した`title`または`original_title`の完全一致
2. ソースコード内のレビュー可能な明示エイリアス一致
3. 公開年が取得できる場合の一致または合理的な近さ
4. 候補が複数残る場合の明示的なTMDB ID override

編集距離だけの曖昧一致、人気度だけの選択、AIによる推測、最初の結果の自動採用は禁止する。
判断できない場合は`unmatched`とする。

安定した例外対応を、正規化タイトルをキーにした小さな管理ファイルへ集約する。

```ts
type TmdbOverride = number | null;
```

- 数値: 人間が確認したTMDB movie ID
- `null`: ライブ中継、舞台挨拶などTMDB映画作品ではないことを明示

overrideには理由をコメントまたはテスト名で残す。Token、ポスターURL全文、取得時刻は
overrideへ保存しない。

### 9.4 生成データ

`Movie`へ、既存コードとの互換性を保ちながら次を追加できるようにする。

```ts
type MoviePosterMetadata = {
  tmdbId?: number;
  posterPath: string;
  posterSource: "tmdb" | "local";
  posterMatchStatus: "matched" | "unmatched" | "not-applicable";
};
```

`matched`では`posterPath`に検証済みTMDB CDN URLを入れる。`unmatched`または
`not-applicable`では、作品名を読み取れる中立的なローカル代替表示を使用する。同じ
「NO IMAGE」画像を大量に並べるだけのUIには戻さない。

TMDB IDと公開可能な画像URLは静的JSONへ含めてよいが、Bearer Tokenは絶対に含めない。

### 9.5 失敗と取得率

次の場合はPagesの更新を失敗させ、前回の正常な公開を維持する。

- Token未設定または認証失敗
- TMDB全体への接続・設定取得失敗
- 取得した画像URLに許可外ホストが含まれる
- 通常映画を含むのにポスター一致が0件

対象作品のポスター取得率が70%未満の場合は、取得率、対象数、一致数、未一致タイトルをログへ
残して明確なwarningを出すが、Pagesの更新は継続する。未一致作品には既存のローカル代替表示を
使用する。

取得率の分母から、overrideで`not-applicable`と確認したライブ中継、コンサート、舞台挨拶、
映画祭イベントを除外できる。単に検索できなかった作品を分母から除外してはならない。

個別の作品が保守的に照合できない場合は、誤った候補を採用せず代替表示で公開できる。実行
ログと完了報告に、対象数、一致数、未一致タイトル、対象外数、取得率を出す。Tokenや認証
ヘッダーは出力しない。

### 9.6 帰属表示

TMDBの承認済みロゴを変更せず使用し、フッターまたはCredits/About相当の場所にTMDBへの
リンクと次の告知文を表示する。

```text
This product uses the TMDB API but is not endorsed or certified by TMDB.
```

TMDBロゴはアプリ自身の名称より目立たせず、色、縦横比、向きの変更を行わない。映画館由来の
上映情報とTMDB由来のポスターを混同しない表示にする。

## 10. Provider構造

映画館固有処理を個別アダプターへ分け、共通の生データ型へ変換する。

概念上の共通フィールドは次のとおりとする。

```ts
type RawScreening = {
  providerId: string;
  theaterId: string;
  theaterName: string;
  sourceUrl: string;
  rawTitle: string;
  date: string;
  startTime: string;
  endTime?: string;
  runtimeMinutes?: number;
  screenName?: string;
  formats: string[];
  salesStatus?: string;
  reservationUrl?: string;
};
```

既存の型名や構造が同等の責務を果たしている場合、名前を合わせるためだけの大規模変更は
行わない。

Providerは、取得、文字コード変換、構造解析、公式URL抽出までを担当する。複数映画館の
統合、作品名正規化、作品ID生成、重複除去、最終スキーマ変換は共通処理へ分離する。

## 11. 日付と時刻

- 対象範囲は`Asia/Tokyo`における今日、明日、明後日とする。
- GitHub ActionsのUTC環境でも日本の日付を基準にする。
- `now`を引数として渡せる設計にしてテスト可能にする。
- ISO日時は時点として解析してから日本時間へ変換する。
- 日付をまたぐ終了時刻や深夜上映を正しく扱う。
- 公式サイトが対象日の予定をまだ公開していない場合、存在しない上映を生成しない。
- UIはデータに存在する日付と3日タブの整合を安全に処理する。

## 12. 作品名正規化

同一作品が映画館ごとの表記差で別作品に分割されないよう、正規化を共通処理で行う。

### 12.1 基本正規化

少なくとも次を順序を固定して適用する。

1. Unicode NFKC正規化
2. 前後空白の除去
3. 全角空白、タブ、連続空白の単一半角空白化
4. 装飾用の`『』`、`「」`、引用符など外側の囲みを除去
5. コロン、スラッシュ、中点、波ダッシュ、ハイフン類などの表記を管理可能な形へ統一
6. 確実に識別できる上映形式を作品名から分離
7. 再度空白と前後記号を整理
8. 明示エイリアスを適用

### 12.2 上映形式の分離

括弧の有無にかかわらず、作品名の先頭または末尾に付く次のような形式を認識できるように
する。

- 字幕、字幕版
- 吹替、吹替版、日本語吹替
- IMAX、IMAXレーザー
- 4DX
- SCREENX
- Dolby Cinema、Dolby Atmos
- 2D、3D

形式は上映回の`formats`へ保持する。形式を除去した結果だけで異なる作品を誤統合しないよう
テストする。

### 12.3 統合方法

作品の統合は次に限定する。

1. 正規化後の完全一致
2. 安全な規則ベース一致
3. レビュー可能な明示エイリアス表
4. 一意性がテストで確認された切り詰め表記の対応

編集距離だけの曖昧一致や生成AIによる自動統合は行わない。似た題名の別作品を統合する
危険があるためである。

公式ページで末尾が`...`などに切り詰められた題名は、他候補に同じ接頭辞がなく、対応が
テストで明示されている場合だけ統合する。判断できない場合は別作品として保持し、ログまたは
検証結果へ警告を出す。

少なくとも、実データで確認された次のような差をテスト対象に含める。

- `Michael/マイケル`、`『Michael マイケル』`、`字幕 Michael マイケル`
- Spider-Manの空白、コロン、副題、字幕・吹替表記
- クレヨンしんちゃんの装飾記号、形式、切り詰め表記
- Star Warsの句読点や区切り記号
- 仮面ライダー／ギャバンの長題・短縮表記

具体的なエイリアスはソースコード上の小さな表へ集約し、理由とテストを付ける。データ取得の
たびに変わる手動IDを生成してはならない。

### 12.4 決定的ID

作品IDは正規化された代表名など安定した入力から決定的に生成する。同じ作品は、取得順、
映画館、実行時刻が変わっても同じIDになる。

ハッシュを使用する場合も、衝突、空文字、Unicodeをテストする。既存の詳細ページURLを
不必要に壊さない。

## 13. 重複除去

同一映画館、同一作品、同一日、同一開始時刻、同一スクリーン、同一形式の上映回が複数回
登録されないようにする。

同じ開始時刻でもスクリーンまたは形式が異なる場合は別上映として保持する。予約URLの有無
だけで上映を重複させず、安全な公式URLを優先して統合する。

## 14. 生成データと情報元

生成JSONには少なくとも次を含める。

- `dataMode`
- `generatedAt`
- `movies`
- `theaters`
- `screenings`
- `sources`
- TMDB ID、ポスターURL、照合状態を含む作品ポスターメタデータ
- ポスター対象数、一致数、対象外数、取得率を含む公開可能な集計

`sources`は各Providerについて次を記録する。

- `providerId`
- `theaterId`
- `theaterName`
- `sourceUrl`
- `fetchedAt`
- `status`
- 必要に応じて取得件数または安全なエラー概要

時刻は機械可読な一貫した形式で保存する。UI表示時に日本語表記へ変換する。

## 15. 更新の原子性と失敗方針

更新処理は次の順番とする。

1. 一時領域へ3館のデータを取得
2. 各Providerの結果を成功または失敗として記録し、成功した解析結果を検証
3. 作品名と上映形式を正規化して重複を除去
4. TMDBで代表作品を保守的に照合し、ポスターを付与
5. 最終スキーマへ変換
6. 上映情報、Token非混入、ポスターURL、照合状態、取得率を検証
7. 1館以上の取得成功と後続処理の成功を確認して最終JSONへ原子的に置換

次の場合は失敗とし、既存の有効データを上書きしない。

- 全3館が取得または解析に失敗
- 対象3館のいずれかが最終データに存在しない
- 必須フィールド欠落
- 不正な日付または時刻
- 重複IDまたは参照切れ
- 許可外URL
- HTMLエラーページや異常なJSON
- 解析構造の重大な変化
- TMDB Token未設定、認証失敗、設定取得失敗
- ポスター取得率が規定値未満
- 生成物またはログへのToken混入

公式側が対象3日すべてをまだ公開していない可能性は考慮する。各日付に必ず上映があると
仮定して架空データを補わない。Providerの結果が全体で0件または取得・解析に失敗した場合、
そのProviderは`failed`として上映を含めない。全Providerが`failed`なら生成全体を失敗させる。

失敗したProviderも対応する映画館と取得元URLを`theaters`と`sources`へ残し、`source.status`を
`failed`にする。UIの映画館カードと映画館詳細には「上映情報を現在取得できません」と表示し、
「0作品を上映」と表示しない。

エラーにはProvider名、映画館名、情報元URL、取得・解析・検証のどの段階かを含める。
Cookie、トークン、レスポンス全文、個人情報は含めない。

## 16. UI表示

### 16.1 実データモード

`dataMode === "real"`では次を表示する。

- 実際の公式上映情報を表示していること
- 最終取得または更新日時
- 情報元映画館名と安全な公式リンク
- 上映予定が変更される可能性
- 購入前に公式サイトで確認する案内
- 正しく照合できたTMDBポスター
- TMDBロゴ、TMDBへのリンク、指定の帰属表示

実データモードで次の表現を表示してはならない。

- デモ上映
- デモ予約ページ
- デモ用リンク
- サンプル上映情報
- DEMO SCHEDULE
- デモポスター

プレースホルダー画像の代替テキストは`ポスター画像なし`など中立的な表現にする。

映画一覧ではポスターを作品識別の中心として2:3で大きく表示し、画像ロード前後でカードが
跳ねないよう寸法を確保する。画面外の画像は遅延読み込みし、最初に見える画像は優先して
読み込む。詳細ページでは同じ作品の`w500`相当ポスターを鮮明に表示する。

TMDB未一致またはイベント上映は、作品名を含む中立的なローカル代替表示にする。全作品へ
同一の「NO IMAGE」画像を並べて完成扱いにしてはならない。外部画像の読み込み失敗時は
1回だけローカル代替表示へ切り替え、エラーループを起こさない。

安全な予約URLがある上映時刻は公式サイトへリンクする。URLがない場合は上映時刻を通常の
テキストまたはボタンではない要素として表示し、クリック可能に見せない。

### 16.2 サンプルモード

`dataMode === "sample"`では次を明記する。

- デモまたはサンプルデータであること
- 実際の上映・予約情報ではないこと
- 予約リンクがデモの場合は、そのことが分かるラベル

### 16.3 共通表示

- 現在の検索、3日タブ、作品詳細、映画館詳細、レスポンシブ表示を維持する。
- 選択日と検索語をURLへ保持する。
- 不正ID、不正日付、空データ、検索結果なしを白画面にしない。
- 外部リンクは公式サイトであることを分かるようにする。
- 見出し、ラベル、フォーカス、キーボード操作、代替テキストを維持する。
- 画面の大規模な再デザインは行わない。

## 17. GitHub ActionsとPages公開

`.github/workflows/deploy-pages.yml`は次のイベントで動作する。

- `main`へのpush
- `workflow_dispatch`
- 定期実行

定期実行はおおむね6時間ごとを上限の目安とし、公式サイトへ過剰にアクセスしない。

公開ビルドは次の順序を守る。

1. checkout
2. Node.jsセットアップ
3. `npm ci`
4. Secretの`TMDB_API_READ_TOKEN`を実データ生成ステップだけへ設定
5. `DATA_MODE=real`で3館の実データ取得とTMDBポスター付与
6. 実データ、ポスター取得率、Token非混入の検証
7. Lint
8. Prettierの変更なしチェック
9. 非watchモードのテスト
10. TypeScriptとViteビルド
11. Pages artifactのアップロード
12. Pagesデプロイ

生成と検証は必ずartifactアップロードより前に行う。ビルド処理がサンプルデータを再生成して
実データを上書きしないようにする。

1館または2館の取得失敗は`sources`へ記録し、成功館の上映データで後続処理とdeployを続ける。
全館取得失敗、TMDB、検証、Lint、整形確認、テスト、型チェック、ビルドのいずれかが失敗した
場合はartifactアップロードとdeployを実行しない。サンプルデータへ切り替えず、直前に成功した
Pagesを維持する。

実データ確認用の別ワークフローは手動実行に限定し、生成JSONと`dist`を短期間のartifactと
して保存できる。ただしPagesへデプロイしない。

ワークフローは最小権限、Pages用concurrency、公式Actions、固定したNodeメジャーバージョン、
lockfileキャッシュを使用する。失敗ログから原因を確認できるようにする。

## 18. Docker仕様

WSLホストへNode.jsやnpmを導入しない。ローカルのJavaScript関連処理はDocker内で行う。

DockerfileはNode.jsビルドステージとNginxランタイムステージを持ち、ビルドステージで次を
実行する。

- `npm ci`
- 指定モードのデータ生成
- データ検証
- Lint
- `format:check`
- `test:run`
- TypeScriptチェック
- Viteビルド

サンプルと実データの双方をビルド引数`DATA_MODE`などで選択できるようにする。ただし、
TMDB TokenはBuildKit secretとして渡し、build argやDockerfileの永続ENVを使わない。

```bash
docker build --build-arg DATA_MODE=sample -t movie-checker:sample .
docker build --build-arg DATA_MODE=real \
  --secret id=tmdb_token,env=TMDB_API_READ_TOKEN \
  -t movie-checker:real .
```

Composeはホスト環境変数`TMDB_API_READ_TOKEN`をBuildKit secretへ受け渡す。値をcompose.yaml、
`.env.example`、ログへ記載しない。実データモードでの起動例:

```bash
DATA_MODE=real docker compose up --build -d
docker compose ps
```

Windows側ブラウザから`http://localhost:8080/`へアクセスできることを確認する。確認後は停止
する。

```bash
docker compose down
```

リポジトリのソースをNginxランタイムへ不要に含めず、`dist`だけを配信する。Nginxには
ヘルスチェックを設定する。
